# Polling Service

Backend-сервис для проведения массовых телевизионных опросов.

Сценарий использования: во время короткого телевизионного ролика зрителю показывается вопрос и QR-код или ссылка. Пользователь переходит на страницу опроса, выбирает вариант ответа и голосует без регистрации.

Сервис рассчитан на короткие опросы с высокой пиковой нагрузкой. В качестве базового сценария предполагается до **100 млн зрителей**, которые могут проголосовать примерно в течение **одной минуты**.

## Возможности

Сервис предоставляет:

- анонимное голосование без регистрации;
- поддержку одиночного и множественного выбора;
- базовую дедупликацию голосов;
- создание опросов через административный API;
- просмотр обезличенных результатов;
- автоматическую проверку доступности опроса по времени;
- Redis для быстрых операций голосования;
- PostgreSQL для постоянного хранения данных;
- периодическую синхронизацию результатов Redis → PostgreSQL;
- горизонтальное масштабирование API-инстансов;
- frontend для голосования и административной работы;
- CORS;
- ограничение частоты запросов;
- Docker Compose для локального запуска.

# Архитектурные решения

## Модульный монолит

Для тестового задания выбран модульный монолит на Go.

Приложение разделено на следующие уровни:

```text
handler
   ↓
service
   ↓
repository
   ↓
storage
```

`handler` отвечает за HTTP-запросы и ответы.

`service` содержит бизнес-логику.

`repository` определяет интерфейсы доступа к данным.

`storage` содержит конкретные реализации для PostgreSQL и Redis.

Такое разделение позволяет изменять инфраструктурные реализации без изменения бизнес-логики.

API-инстансы не хранят состояние голосования локально, поэтому приложение можно запускать в нескольких экземплярах за Nginx.

---

# Repository / Storage

`internal/repository` содержит интерфейсы:

```text
repository
    │
    ├── PollRepository
```

Конкретные реализации находятся в:

```text

└── redis/
```

Бизнес-логика не зависит напрямую от PostgreSQL или Redis.

# PostgreSQL

PostgreSQL используется как постоянное хранилище.

Основные таблицы:

```text
polls
  │
  └── poll_options

poll_results
```

### `polls`

Хранит информацию об опросе:

- идентификатор;
- вопрос;
- тип опроса;
- время начала;
- время окончания;
- статус;
- время создания и изменения.

### `poll_options`

Хранит варианты ответа:

- идентификатор;
- идентификатор опроса;
- текст варианта.

### `poll_results`

Хранит агрегированные результаты:

- `poll_id`;
- `option_id`;
- количество голосов;
- время последнего обновления.

Индивидуальные голоса в PostgreSQL не сохраняются.

---

# Redis

Redis используется для операций, которые должны выполняться максимально быстро во время короткого периода голосования.

В Redis хранятся:

- ключи дедупликации по `client_id`;
- счётчики голосов по вариантам ответа.

Основная операция голосования выполняется атомарно с помощью Lua-скрипта.

Упрощённо логика выглядит так:

```text
client_id уже голосовал?
        │
   ┌────┴────┐
   │         │
  да        нет
   │         │
   ▼         ▼
  409      записать
           client_id
              │
              ▼
          увеличить
           счётчики
              │
              ▼
             201
```

Проверка дедупликации и увеличение счётчиков выполняются внутри одной атомарной операции Redis.

Поэтому два параллельных запроса одного клиента не смогут оба пройти проверку дедупликации.

---

# Дедупликация

Регистрация пользователей не требуется.

При первом обращении backend создаёт случайный `client_id` и сохраняет его в cookie.

```text
client_id = UUID
```

При голосовании идентификатор используется для проверки повторного голосования.

Для ключа дедупликации устанавливается TTL, соответствующий времени действия опроса.

Дедупликация намеренно является базовой. Она предназначена для предотвращения обычного повторного голосования, а не для полноценной защиты от мотивированного злоумышленника.

IP-адрес не используется как идентификатор пользователя, поскольку несколько пользователей могут находиться за одним NAT, мобильной сетью или Wi-Fi.

IP используется только для ограничения частоты запросов.

# Типы опросов

Сервис поддерживает два типа опросов.

### `single`

Пользователь может выбрать только один вариант.

Пример запроса:

```json
{
  "option_ids": [11]
}
```

### `multiple`

Пользователь может выбрать несколько вариантов.

Пример:

```json
{
  "option_ids": [11, 12]
}
```

Backend дополнительно проверяет соответствие количества выбранных вариантов типу опроса.

Для обоих типов один `client_id` может проголосовать за конкретный опрос только один раз.

# Почему без Kafka

Kafka в текущем решении не используется.

Основная операция голосования представляет собой:

```text
проверка дедупликации
        +
атомарное увеличение счётчиков
```

Redis предоставляет необходимые примитивы непосредственно.

Добавление Kafka увеличило бы количество компонентов и сложность системы, но не решало бы обязательную задачу текущего тестового задания.

Kafka могла бы быть полезна при появлении дополнительных асинхронных потребителей:

- аналитика;
- аудит;
- потоковая обработка;
- отправка событий во внешние системы;
- отдельные сервисы статистики.

Для текущего сценария Kafka не является обязательным компонентом.

# Синхронизация результатов

Во время голосования Redis хранит актуальные агрегированные счётчики.

Периодически `ResultSync` получает текущие значения счётчиков из Redis и записывает их в PostgreSQL.

```text
Redis
  │
  │ текущее значение счётчика
  ▼
ResultSync
  │
  ▼
PostgreSQL
```

В PostgreSQL значение `votes_count` заменяется текущим значением Redis.

Например:

```text
Redis:      157
PostgreSQL: 120

        ↓ sync

Redis:      157
PostgreSQL: 157
```

Повторная синхронизация не добавляет `157` к существующему значению, а устанавливает его как актуальное:

```text
PostgreSQL: 157
Redis:      157

        ↓ sync

PostgreSQL: 157
```

Таким образом, синхронизация не создаёт дополнительные голоса при повторном запуске.

# Состояние опроса

Доступность опроса определяется по времени.

```text
now < starts_at
        │
        ▼
  ещё не начался

starts_at <= now < ends_at
        │
        ▼
      active

now >= ends_at
        │
        ▼
     finished
```

При голосовании backend проверяет `starts_at` и `ends_at`.

Дополнительно при создании опроса проверяется корректность временного интервала и отсутствие пересечения с существующими опросами.

# Масштабирование

Перед API используется Nginx:

```text
                    ┌── API-1
Client → Nginx ─────┤
                    └── API-2
```

API-инстансы не хранят состояние голосования локально.

Общее состояние находится в Redis и PostgreSQL.

Поэтому количество API-инстансов можно увеличить:

```text
Nginx
 ├── API-1
 ├── API-2
 ├── API-3
 └── API-N
```

Для production-сценария с заявленной нагрузкой Redis и PostgreSQL также потребовали бы отдельного масштабирования, репликации и настройки отказоустойчивости.

Локальная конфигурация проекта использует одиночные экземпляры этих компонентов.

## Конфигурация

Перед запуском приложения необходимо создать файл `.env` в корне проекта.

Пример:

```env
HTTP_PORT=8080

POSTGRES_DSN=postgres://postgres:postgres@postgres:5432/polls

REDIS_ADDR=redis:6379

ADMIN_TOKEN=admin-secret

RATE_LIMIT_RPS=10
```

Описание переменных:

| Переменная | Описание |
|---|---|
| `HTTP_PORT` | Порт HTTP-сервера |
| `POSTGRES_DSN` | Строка подключения к PostgreSQL |
| `REDIS_ADDR` | Адрес Redis |
| `ADMIN_TOKEN` | Токен для доступа к административному API |
| `RATE_LIMIT_RPS` | Максимальное количество запросов от одного IP за окно в 1 секунду |

Все параметры обязательны.

`RATE_LIMIT_RPS` должен быть положительным целым числом.

### Rate Limit

Rate limit применяется на уровне HTTP middleware и ограничивает количество запросов от одного IP-адреса.

Например:

```env
RATE_LIMIT_RPS=10
```

означает, что один IP может выполнить не более 10 запросов за окно длительностью 1 секунду.

При превышении лимита сервер возвращает:

```http
429 Too Many Requests
```

Rate limit используется как дополнительная защита от большого количества запросов и не используется для определения уникальности пользователя при голосовании.

Для дедупликации голосов используется `client_id`, сохраняемый в cookie.

Текущая реализация использует fixed-window алгоритм с окном в 1 секунду.

# API

## Public API

### Получить активный опрос

```http
GET /api/v1/polls/active
```

Возвращает текущий активный опрос.

Если активного опроса нет:

```http
404 Not Found
```

### Получить опрос

```http
GET /api/v1/polls/{id}
```

### Проголосовать

```http
POST /api/v1/polls/{id}/vote
Content-Type: application/json
```

Тело запроса:

```json
{
  "option_ids": [11]
}
```

Для множественного выбора:

```json
{
  "option_ids": [11, 12]
}
```

При успешном голосовании:

```http
201 Created
```

Если пользователь уже голосовал:

```http
409 Conflict
```

Если выбранные варианты некорректны или опрос недоступен:

```http
400 Bad Request
```

# Frontend

В проекте реализован простой frontend для пользовательского и административного сценариев.

Пользовательская страница:

```text
QR-код / ссылка
       │
       ▼
Frontend
       │
       ▼
GET /api/v1/polls/active
       │
       ▼
Вопрос + варианты ответа
       │
       ▼

       │
```

Frontend отображает пользователю порядковый номер варианта, а в API передаёт фактический `option_id`.

- анализ необходимости Kafka;

AI-артефакты используются для фиксации архитектурных решений и процесса их проработки, а итоговая реализация проверялась и адаптировалась под фактический код проекта.

# Ограничения решения

Проект является тестовым и использует упрощённые production-механизмы.

### Дедупликация

`client_id` в cookie не является надёжным способом идентификации пользователя и может быть сброшен или изменён.

Выбранный механизм предназначен для базовой защиты от повторного голосования обычными пользователями.

### Redis

В локальной конфигурации используется один экземпляр Redis.

Для production потребовалась бы отказоустойчивая конфигурация Redis и соответствующее масштабирование.

### PostgreSQL

Для локального запуска используется один экземпляр PostgreSQL.

При реальной нагрузке потребовались бы репликация, резервирование и дополнительная настройка производительности.

### Административная авторизация

Для тестового задания используется простой `X-Admin-Token`.

Для production-системы потребовались бы полноценная аутентификация, авторизация, управление администраторами и ротация credentials.

# Почему выбран такой подход

Основная нагрузка приходится на короткий период голосования, поэтому критическая операция должна быть максимально простой:

```text
получить запрос
      ↓
проверить poll
      ↓
проверить варианты
      ↓
проверить client_id
      ↓
атомарно увеличить счётчики
      ↓
вернуть результат
```

Redis подходит для быстрых атомарных операций и временных данных, а PostgreSQL используется как постоянное хранилище структуры опросов и агрегированных результатов.

Разделение интерфейсов репозиториев и конкретных storage-адаптеров позволяет тестировать бизнес-логику независимо от инфраструктуры.

Несколько экземпляров Go API позволяют горизонтально масштабировать stateless-часть приложения.

В результате архитектура остаётся достаточно простой для тестового задания и при этом содержит основные механизмы, необходимые для обработки большого количества одновременных голосов.
