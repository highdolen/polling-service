# Архитектура Polling Service

## 1. Требования

В рамках задания необходимо разработать backend-сервис для проведения массовых телевизионных опросов.

Основной сценарий:

1. Во время короткого телевизионного ролика пользователю показывается вопрос.
2. Рядом с вопросом отображается QR-код или ссылка.
3. Пользователь переходит на страницу опроса.
4. Регистрация не требуется.
5. Пользователь выбирает один или несколько вариантов ответа.
6. Результаты доступны администратору в обезличенном виде.

Предполагается высокая пиковая нагрузка: до 100 млн зрителей потенциально могут принять участие в голосовании примерно в течение одной минуты.

При этом полноценная защита от мотивированных злоумышленников не является основной задачей. Требуется базовая защита от обычного повторного голосования.

---

## 2. Рассмотренные варианты архитектуры

На этапе проектирования рассматривались два основных варианта:

- модульный монолит;
- микросервисная архитектура.

Микросервисный вариант позволил бы разделить систему на несколько независимых сервисов, например:

```text
Poll Service
Vote Service
Result Service
Analytics Service
```

Однако для текущего тестового задания такое разделение увеличило бы количество инфраструктурных компонентов и сложность взаимодействия между ними.

Основная операция голосования относительно небольшая:

```text
проверить опрос
      ↓
проверить client_id
      ↓
атомарно увеличить счётчик
```

Поэтому выбран модульный монолит с возможностью горизонтального масштабирования.

---

## 3. Выбранная архитектура

Приложение реализовано как модульный монолит на Go.

Основные уровни:

```text
Handler
   ↓
Service
   ↓
Repository
   ↓
Storage
```

### Handler

Отвечает за HTTP-взаимодействие:

- получение HTTP-запросов;
- декодирование входных данных;
- вызов сервисного слоя;
- формирование HTTP-ответов;
- обработку ошибок.

### Service

Содержит бизнес-логику приложения:

- создание опросов;
- проверку временных интервалов;
- проверку вариантов ответа;
- обработку голосов;
- получение результатов.

### Repository

Содержит интерфейсы доступа к данным.

Сервисный слой работает с интерфейсами, а не напрямую с PostgreSQL или Redis.

### Storage

Содержит конкретные реализации работы с инфраструктурой:

```text
PostgreSQL
Redis
```

Такое разделение позволяет изолировать бизнес-логику от конкретных технологий хранения данных.

---

## 4. PostgreSQL

PostgreSQL выбран как постоянное хранилище данных.

В базе используются следующие основные сущности:

```text
polls
  │
  └── poll_options

poll_results
```

### `polls`

Содержит:

- идентификатор опроса;
- вопрос;
- тип опроса;
- время начала;
- время окончания;
- статус;
- время создания и изменения.

### `poll_options`

Содержит:

- идентификатор варианта;
- идентификатор опроса;
- текст варианта ответа.

### `poll_results`

Содержит агрегированные результаты:

- `poll_id`;
- `option_id`;
- `votes_count`;
- время последнего обновления.

Индивидуальные голоса в PostgreSQL не сохраняются.

Это позволяет не создавать отдельную запись в базе для каждого голоса.

---

## 5. Redis

Redis используется для операций, которые должны выполняться быстро во время короткого периода голосования.

В Redis хранятся:

- ключи дедупликации;
- текущие счётчики голосов.

Основная операция голосования выполняется с помощью Lua-скрипта.

Упрощённая логика:

```text
проверить deduplication key
        ↓
если ключ существует
        ↓
   повторный голос

если ключа нет
        ↓
создать deduplication key
        ↓
увеличить счётчики
        ↓
   успешный голос
```

Проверка дедупликации и увеличение счётчиков выполняются в одном атомарном Lua-скрипте.

Это позволяет избежать ситуации, когда два параллельных запроса одного клиента одновременно проходят проверку дедупликации.

Подробное описание механизма находится в:

```text
ai/deduplication.md
```

---

## 6. Repository / Storage

Для отделения бизнес-логики от инфраструктуры используются интерфейсы repository.

```text
internal/repository/
├── poll.go
├── result.go
├── result_reader.go
└── vote.go
```

Конкретные реализации находятся в:

```text
internal/storage/
├── postgres/
└── redis/
```

Например, сервис голосования работает с:

```go
VoteRepository
```

и не знает, каким образом конкретная реализация взаимодействует с Redis.

Это позволяет:

- изолировать бизнес-логику;
- использовать mock-реализации в тестах;
- менять конкретное хранилище без изменения сервисного слоя.

---

## 7. Синхронизация результатов

Во время активного голосования Redis используется для хранения актуальных агрегированных счётчиков.

Отдельный компонент `ResultSync` периодически переносит текущие значения в PostgreSQL.

Схема:

```text
Redis
  │
  │ current counter
  ▼
ResultSync
  │
  ▼
PostgreSQL
```

Например:

```text
Redis:      157
PostgreSQL: 120

        ↓ sync

Redis:      157
PostgreSQL: 157
```

При следующей синхронизации:

```text
Redis:      157
PostgreSQL: 157

        ↓ sync

PostgreSQL: 157
```

В PostgreSQL устанавливается текущее абсолютное значение счётчика.

Синхронизация не выполняет операцию вида:

```text
votes_count = votes_count + redis_count
```

Поэтому повторный запуск синхронизации не приводит к повторному начислению голосов.

## 8. Nginx и горизонтальное масштабирование

Перед API используется Nginx.

```text
                    ┌── API-1
Client → Nginx ─────┤
                    └── API-2
```

API-инстансы не хранят состояние голосования локально.

Общее состояние находится в:

```text
Redis
PostgreSQL
```

Поэтому можно запускать несколько экземпляров API:

```text
Nginx
 ├── API-1
 ├── API-2
 ├── API-3
 └── API-N
```

Все экземпляры работают с одним Redis и PostgreSQL.

Это позволяет горизонтально масштабировать stateless-часть приложения без изменения бизнес-логики.

## 10. Поток голосования

Основной сценарий голосования:

```text
Browser
   │
   │ POST /api/v1/polls/{id}/vote
   ▼
Nginx
   │
   ▼
Go API
   │
   ├── проверка poll
   ├── проверка времени
   ├── проверка вариантов
   └── проверка rate limit
   │
   ▼
Vote Service
   │
   ▼
Vote Repository
   │
   ▼
Redis Lua Script
   │
   ├── проверка client_id
   ├── создание deduplication key
   └── увеличение счётчиков
   │
   ▼
HTTP 201
```

Если `client_id` уже голосовал, Redis возвращает отрицательный результат и сервис возвращает:

```http
409 Conflict
```

---

## 11. Типы опросов

Сервис поддерживает два типа опросов.

### Single

Пользователь может выбрать только один вариант.

```json
{
  "option_ids": [11]
}
```

Frontend использует radio buttons.

Backend дополнительно проверяет, что для опроса типа `single` передан ровно один вариант.

### Multiple

Пользователь может выбрать несколько вариантов.

```json
{
  "option_ids": [11, 12]
}
```

Frontend использует checkbox.

Backend проверяет существование всех переданных вариантов и не допускает повторяющиеся `option_id`.

При этом дедупликация выполняется один раз для всего голоса.

---

## 12. Состояние опроса

Отдельный scheduler для переключения состояния опроса не используется.

Доступность определяется на основании:

```text
starts_at
ends_at
current time
```

Логика:

```text
now < starts_at
        │
        ▼
  ещё не начался

starts_at <= now < ends_at
        │
        ▼
      active

now >= ends_at
        │
        ▼
     finished
```

При голосовании сервис проверяет время непосредственно перед выполнением операции в Redis.

Кроме того, при создании опроса проверяется корректность временного интервала и отсутствие пересечения с другим опросом.

---

## 13. Почему без Kafka

Kafka рассматривалась как возможный компонент для асинхронной обработки событий голосования.

Однако основная операция голосования не требует отдельного брокера:

```text
проверка дедупликации
        +
увеличение счётчиков
```

обе операции выполняются непосредственно в Redis и объединены в один Lua-скрипт.

Добавление Kafka привело бы к появлению дополнительных компонентов:

```text
Go API
   ↓
Kafka Producer
   ↓
Kafka
   ↓
Kafka Consumer
   ↓
Redis / PostgreSQL
```

Для текущего тестового задания такая схема увеличила бы сложность без обязательной необходимости.

Kafka могла бы быть полезна при расширении системы, например для:

- аналитики;
- аудита;
- потоковой обработки событий;
- интеграции с внешними системами;
- отдельных сервисов статистики.

---

## 14. Масштабирование

Основным масштабируемым компонентом является Go API.

```text
                 Nginx
              /    |    \
             /     |     \
          API-1  API-2  API-N
             \     |     /
              \    |    /
               Redis
                  │
             PostgreSQL
```

API не хранит локальные результаты голосования.

Это позволяет добавлять новые API-инстансы независимо от других экземпляров.

Однако Redis и PostgreSQL остаются общими компонентами инфраструктуры.

Для production-сценария с очень высокой нагрузкой потребовались бы дополнительные механизмы:

- Redis Cluster или другая отказоустойчивая конфигурация;
- репликация PostgreSQL;
- балансировка и масштабирование базы данных;
- мониторинг;
- резервирование;
- централизованное логирование.

В рамках тестового задания используется упрощённая конфигурация с одним Redis и PostgreSQL.

---

## 15. Административный API

Административные операции отделены от публичного API.

Основные операции:

```text
создание опроса
       ↓
получение списка опросов
       ↓
получение результатов
```

Административный API защищён статическим токеном из переменной окружения `ADMIN_TOKEN`.

Для тестового задания этого достаточно, поскольку полноценная система управления администраторами не является частью требований.

---

## 16. Frontend

В проекте реализован простой frontend.

Пользовательский сценарий:

```text
QR-код / ссылка
       ↓
Frontend
       ↓
GET /api/v1/polls/active
       ↓
Вопрос + варианты
       ↓
Выбор ответа
       ↓
POST /api/v1/polls/{id}/vote
       ↓
Результат голосования
```

Frontend поддерживает оба типа опросов:

```text
single   → radio
multiple → checkbox
```

Административная страница используется для работы с опросами и просмотра результатов.

---

## 17. CORS и Rate Limit

Для HTTP API реализованы middleware:

```text
CORS
Rate Limit
Admin Auth
```

CORS позволяет frontend взаимодействовать с API при необходимости размещения frontend и backend на разных origins.

Rate limit используется как дополнительная базовая защита от слишком большого количества запросов с одного источника.

При этом IP не используется для определения уникальности пользователя.

---

## 18. Тестирование

Бизнес-логика и HTTP-слой покрыты тестами.

Структура:

```text
tests/
├── service/
├── handler/
└── integration/
```

Service tests проверяют бизнес-правила.

Handler tests проверяют HTTP-обработчики и ответы.

Integration test проверяет работу механизма голосования с Redis.

Для запуска:

```bash
go test ./...
```

---

## 19. Ограничения

Архитектура является решением для тестового задания.

Некоторые production-механизмы намеренно упрощены.

Основные ограничения:

- один Redis в локальной конфигурации;
- один PostgreSQL;
- простой `X-Admin-Token`;
- базовая дедупликация через `client_id`;
- отсутствие полноценной anti-fraud системы;
- отсутствие мониторинга и централизованного логирования;
- ограниченное количество API-инстансов в локальном Docker Compose.

Эти ограничения позволяют сохранить относительно небольшую и понятную кодовую базу.

Итоговая архитектура:

```text
                         ┌─────────────────┐
                         │     Browser     │
                         │    Frontend     │
                         └────────┬────────┘
                                  │
                                  ▼
                         ┌─────────────────┐
                         │      Nginx      │
                         │ Reverse Proxy / │
                         │ Load Balancer   │
                         └────────┬────────┘
                                  │
                       ┌──────────┴──────────┐
                       │                     │
                       ▼                     ▼
                ┌──────────────┐      ┌──────────────┐
                │    API-1     │      │    API-2     │
                │     Go       │      │     Go       │
                └──────┬───────┘      └──────┬───────┘
                       │                     │
              ┌────────┴─────────────────────┴────────┐
              │                                        │
              ▼                                        ▼
       ┌──────────────┐                        ┌──────────────┐
       │    Redis     │                        │  PostgreSQL  │
       │              │                        │              │
       │ Deduplication│                        │ Polls        │
       │ Counters     │                        │ Options      │
       │ Hot results  │                        │ Results      │
       └──────┬───────┘                        └──────▲───────┘
              │                                       │
              │                                       │
              └──────────────┐     ┌──────────────────┘
                             ▼     │
                       ┌──────────────┐
                       │ Result Sync  │
                       │              │
                       │ Redis →      │
                       │ PostgreSQL   │
                       └──────────────┘
```

Выбранный вариант позволяет сохранить простую структуру приложения, отделить бизнес-логику от инфраструктуры и масштабировать stateless API горизонтально.

При этом наиболее критичная операция голосования выполняется атомарно в Redis, а PostgreSQL используется как постоянное хранилище структуры опросов и агрегированных результатов.
